BUG ARCH-01: Registration Flow Flaw (Critical)
======================================================================

SEVERITY: Critical
STATUS:   RESOLVED

DESCRIPTION:
The original POST /api/v1/auth/register endpoint inserted user data
directly into PostgreSQL BEFORE verifying email ownership via OTP.
This violated the Zero-Trust architecture and could lead to:
  - Spam accounts (bots registering fake emails)
  - Orphan accounts (unverified emails consuming DB space)
  - Database pollution (invalid data in 4 tables simultaneously)

ROOT CAUSE:
Single endpoint handled both OTP generation AND DB insertion.
No email ownership verification gate existed before DB write.

RESOLUTION: Redis-Hold Pattern (2-Step Registration)
Replaced single /register endpoint with two strictly dependent endpoints:

Step 1: POST /api/v1/auth/register/init
  - Validates input payload
  - Checks if email already registered in PostgreSQL (BUG-02 fix)
  - Checks if registration already pending in Redis
  - Generates 6-digit OTP
  - Stores ENTIRE payload + hashed OTP in Redis (Key: reg_pending:<email>)
  - TTL: 300 seconds (5 minutes)
  - Sends OTP via Nodemailer (Ocean Blue template)
  - ZERO PostgreSQL INSERT — no database pollution

Step 2: POST /api/v1/auth/register/complete
  - Validates OTP against Redis reg_pending:<email>
  - On success: retrieves stored payload from Redis
  - Executes BEGIN...COMMIT transaction in PostgreSQL
  - Inserts into 4 tables atomically (users, profiles, relationships, consents)
  - On failure: ROLLBACK entire transaction
  - Deletes Redis key on success
  - Returns handles + child PIN

  2. src/services/registration.service.ts  | 1.0.0 → 1.1.0 | UPDATED

BUG-02: OTP Sent to Already Registered Email (Medium)
======================================================================

SEVERITY: Medium
STATUS:   RESOLVED

DESCRIPTION:
After ARCH-01 fix, the /register/init endpoint checked Redis for
pending registration but did NOT check PostgreSQL for existing users.
This caused OTP to be sent to already registered emails. When the user
entered the OTP in /register/complete, the DB transaction failed with
"duplicate key value violates unique constraint uq_users_email".

Result: User received OTP but could never complete registration.
        Wasted OTP, confusing UX, unnecessary Redis storage.

ROOT CAUSE:
initiateRegistration() function in redis-hold.service.ts had only
one check: Redis pending key. No PostgreSQL SELECT on users table.

RESOLUTION:
Added PostgreSQL email existence check as FIRST validation gate in
initiateRegistration():

  CHECK 1: PostgreSQL — does email exist in auth_schema.users?
           YES → Return error: "This email is already registered."
           NO  → Continue

  CHECK 2: Redis — is registration already pending for this email?
           YES → Return error: "Already in progress."
           NO  → Continue

  CHECK 3: Both clear → Generate OTP, store in Redis, send email

Now OTP is NEVER sent to already registered emails.

FILE MODIFIED:
  src/services/redis-hold.service.ts | 1.0.0 → 1.0.1

COMMIT:
  28252f5 fix(auth): add email existence check in postgresql before sending registration otp
